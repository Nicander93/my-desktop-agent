# 文档维护

本文定义项目文档的入口、归属和更新约束。架构与实际行为发生冲突时，以当前源码和测试为准，并在同次改动中修正文档或明确记录差异。

## 文档层次

- 根 `README.md`：项目定位、安装和最短使用路径，不复制各层实现细节。
- `docs/`：Agent 上下文与开发入口；具体规格统一放在 `docs/specs/`。
- `docs/archive/`：已被替代但仍需追溯的项目级历史文档；归档条件见其 [README](../docs/archive/README.md)。
- `contributing/`：贡献者必须遵守的分层、IPC、测试、代码与注释规范。
- `apps/*/README.md`、`packages/*/README.md`、`scripts/README.md`：包或脚本的职责、边界、常见修改入口和运行限制。

同一事实只维护一个权威说明；其他文档通过链接引用。API 或行为细节应靠近代码，文档解释跨文件约束、设计原因和修改路径。

领域已有自己的历史索引时继续就近归档，例如 `docs/eval/archive/`。不要仅因文档较旧就移动它；归档前必须确认替代入口并更新有效引用。

## 何时同步更新

- 新增或修改 IPC：更新 shared 契约、handler/preload/renderer 类型，并检查 `contributing/ipc-contract.md` 的 channel 或流程说明。
- 修改 Session、Profile、流式、权限或路径策略：更新受影响的源码 JSDoc、包 README 和相关规格链接。
- 新增包、脚本或公开入口：增加或更新对应 README，注明输入、输出、副作用、平台条件与恢复方式。
- 变更长期架构决策：在 `docs/adr/` 建立 ADR；普通实现细节不要创建 ADR。
- JSON、锁文件和生成物不能写注释时：在邻近 README 或本文件体系中记录原因，不能破坏格式。

## 链接与可验证性

使用相对链接，链接目标必须存在。代码中只引用稳定的文档入口，避免把短期计划当成永久规范。提交前运行 `pnpm check`；Markdown 链接检查接入前，至少使用仓库搜索或本地 Markdown 检查确认新增链接路径有效。

## 审阅清单

- 变更是否更新了唯一的权威文档，而非复制粘贴多份说明？
- 新增或改过的公共 API、核心类型和复杂路径需要额外契约时，是否使用了英文多行 TSDoc？
- 包 README 是否仍准确说明层级边界、入口和运行限制？
- 链接是否相对、有效且指向读者真正需要的入口？
